# Milestone v1.4: 播放可用性与生产自愈闭环

**Status:** ✅ SHIPPED 2026-08-10

**Closeout:** `override_closeout` (backfilled after v1.5 kickoff)

## Overview

v1.4 将 v1.3 已验证的受控 crawler control plane 延伸到播放可用性和生产自愈闭环：先把 metadata、source health 与实际 playback 分成可审计的状态层，再完成本地 `repair_players` vertical slice、MovieDetail/Player 状态闭环、GitHub Actions 生产修复与 reconciliation，最后用独立 fresh production tuple 证明 Dashboard → Viewer → 实际播放。生产 Puppeteer 继续运行在 GitHub Actions，历史 Phase 13 carrier 保持 frozen。

- [x] 20-03 — Admin/MovieDetail DTO、Dashboard 与 Player no-source guard

**Success criteria:**

## Milestone Summary

**Key decisions:**

- metadata persisted、source transport/health、repair execution、receipt/readback 和 actual playback 保持独立事实层。
- `repair_players` 采用 server-owned operation registry、revision/CAS、bounded observation 和 validated receipt，不开放任意 URL、命令或 workflow。
- 本地 Gateway 与 GitHub Actions production runner 复用同一 D1 task/run/attempt/lease/provider 控制面，生产浏览器继续在 Actions 执行。
- `playback_verified` 采用 fail-closed 规则，必须有显式 Play、allowlisted media events 和正向 `currentTime` progress；fixture 或 provider success 不单独升级播放状态。
- Phase 24 使用 fresh tuple 完成 Dashboard → Viewer → playback 证据链，历史 Phase 13 carrier 保持冻结。

**Issues resolved:**

- `SUN-064 players=0` 不再被 metadata receipt 当作可播放成功，经过 source readiness、repair 和 readback 边界处理。
- Dashboard、MovieDetail 和 Player 的 source/readiness/action 状态形成同 identity 的可见闭环。
- GitHub Actions repair 的 provider binding、签名回调、retry/reconciliation、receipt 和 current-attempt 投影形成闭环。

**Issues deferred / technical debt:**

- 归档时全局 `audit-open` 仍列出 11 个历史或当前 debug sessions；它们不属于 v1.4 的 requirement evidence，继续在 `.planning/STATE.md` 中跟踪。
- `@starye/config` 的 CI lint baseline 继续作为独立、非因果技术债。
- 历史 Phase 13 selected-production Viewer proof 继续冻结；v1.4 的 fresh tuple 证据独立完成。
