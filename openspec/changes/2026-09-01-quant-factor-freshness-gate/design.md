## Context

研究报告快照已经保存每条证据的 `observedAt`，因子模型保存证据 key 和权重，研究摘要与决策助手也都在服务端校验 AI 的因子引用。当前缺口是这条事实链没有形成统一的因子级时间闸门，导致研究摘要、决策助手和因子数据健康视图各自使用不同的时间语义。

## Goals / Non-Goals

**Goals:**

- 使用报告快照中的证据时间计算可复现的因子新鲜度。
- 统一研究摘要和今日决策助手的 AI 因子接受规则。
- 让响应和页面同时表达字段完整性、来源状态、新鲜度和 AI 是否实际纳入。
- 保持旧报告、旧摘要和旧客户端响应可读。

**Non-Goals:**

- 不把新鲜度直接改写成买入、卖出或持仓动作。
- 不新增数据库字段、表、迁移、provider 或后台定时任务。
- 不让模型自报的新鲜度、权重或分数成为事实来源。

## Decisions

### 1. 因子周期而非单一全局周期

服务端新增版本化 `quant-factor-freshness-v1` 纯函数。趋势和风险使用 3 天内为最新、10 天内需复核；估值使用 14 天/60 天；股东回报使用 30 天/180 天；盈利质量使用 180 天/365 天。边界按 UTC 日期计算，未来、缺失、无效观察时间统一为 `unknown`。每个因子取所有必需 evidence key 中最旧的有效观察时间，缺一项即不能宣称完整新鲜度。

选择因子周期是因为证据的经济更新频率不同；统一 48 小时规则会把季度财报误报为行情过期，而完全不检查又会放过短线日线失效。

### 2. 服务端重算 AI 接受状态

`buildQuantAiFactorImpact` 接收一次性评估时间，返回因子 freshness、汇总阻断因子和 AI 新鲜度资格。`accepted` 只在因子状态完整、分数有效、置信度达标、引用属于该因子且至少引用可用证据、因子 freshness 为 `fresh` 时成立。旧持久化摘要的派生影响按当前读取时间重算；决策助手快照的审计影响按评估时间重算，保持历史快照内部一致。

### 3. 客户端保守兼容

API 新字段在客户端解析器中为可选。新响应展示服务端提供的新鲜度；旧响应缺字段时使用 `unknown`，仍保留原有确定性结果和 AI 文本。因子数据健康在无 AI 摘要时也独立从报告证据计算新鲜度，避免只有点击 AI 后才出现关键数据状态。

### 4. 明确 UI 语义

因子行同时显示“字段状态”“来源状态”“新鲜度”和“AI 纳入状态”。`aging` 提示复核，`stale/unknown` 明确阻断 AI 纳入；这些状态不替代信号分数或推荐标签。

## Risks / Trade-offs

- [周期依赖领域经验] → 周期与版本号显式返回，页面显示实际年龄和阈值，后续调整可通过新版本回溯。
- [不同入口时间不同] → 研究摘要使用当前读取时间做当前资格判断，决策助手使用快照评估时间做历史审计，均在响应中保留观察时间。
- [双端纯函数存在维护风险] → 服务端字段作为 API 权威值，客户端仅用于无摘要页面展示，并以相同版本常量和边界测试约束。

## Migration Plan

无需数据库迁移。发布后新研究摘要和决策助手响应带有因子新鲜度；旧 JSON 在读取时继续解析，缺字段显示为未知并保留确定性结论。回滚代码即可恢复旧响应生成逻辑，不改变已存数据。
