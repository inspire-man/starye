## Context

候选对比抽屉已经维护 2 至 3 只候选的稳定选择，并通过 `quantApi.generateResearchRun` 支持单只研究运行。研究运行接口已经负责报告生成、持久化和权威读回，因此本 change 只增加前端批量编排和可见状态。

## Goals / Non-Goals

**Goals:**

- 让对比后的候选可以一次进入研究运行。
- 保持最多 3 项、最多 2 个并行请求，并提供逐项实时状态。
- 在部分失败时保留成功结果和可重试入口。

**Non-Goals:**

- 不新增批量 API，不改变研究报告或研究评分公式。
- 不把多个股票合并成一份报告，也不修改历史研究运行。
- 不在批量操作中自动修改观察池、研究标记或候选排序。

## Decisions

### 1. 复用单股票 API

前端调用已有单股票研究运行接口，由服务端继续执行用户隔离、provider 错误处理和 D1 readback。新增后端批量 endpoint 会复制已有契约并扩大失败语义，当前 2 至 3 项范围没有必要。

### 2. 独立的有界编排器

新增纯 TypeScript `runResearchBatch`，输入候选代码、单项 runner 和进度回调，内部最多启动两个 worker，并按输入顺序返回结果。这样并发上限和部分失败行为可以在不依赖 Vue 或网络的测试中验证。

### 3. 状态按股票代码归属

App 使用 `Record<string, BatchResearchItemState>` 保存批次状态，以 `tsCode` 作为稳定键。每次进度回调只更新对应行；成功项保留返回的 `QuantResearchRun`，失败项保留原始错误供统一错误解析显示。

### 4. 批次状态不替代详情历史

批量面板只反馈本次操作结果。用户点击候选行后仍通过既有详情加载流程读取该股票的最新研究历史；再次批量运行只替换面板当前批次，不删除旧运行。

## Risks / Trade-offs

- [某个请求长时间占用 worker] -> 并发上限小且页面显示进行中；现有 API 的请求边界继续负责超时。
- [对比抽屉关闭后请求仍返回] -> 状态只写入按代码分组的本地批次，重新打开仍可看到最近一次批次结果，不触发其他页面数据重置。
- [同一候选同时被详情页生成] -> 两者均是独立研究运行，数据库保留历史；按钮只防止批量入口自身重复启动。

## Migration Plan

只部署 Quant Pages 静态资源，不需要 API、D1 或 bridge migration。回滚时移除批量入口即可，已经生成的研究运行继续由现有历史 API 读取。
